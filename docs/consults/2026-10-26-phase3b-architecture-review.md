# Phase 3B architecture review — 2026-10-26

The core Cosmos design is appropriate for the requested experience. Keep searchable image meaning in the existing chunk container, colocated with the vector and filter metadata; keep image bytes and full extraction artifacts in Blob storage. Retain library-scoped queries and document-scoped lifecycle operations. The review found a publication race and several retrieval/processing issues. The findings below describe the pre-fix implementation. They do not justify a new image container or a separate vector database.

This assessment covers the implemented source, the project's measured invariants, current Microsoft documentation, the existing live smoke record and five controlled local reproductions. The implementation and deployment were left unchanged during this review. Numerical evidence is in [the review record](../../records/phase3b-architecture-review-20261026.json); the previous live evidence remains [the smoke record](../../records/phase3b-images-20261026.json).

**Follow-up resolution.** Reproduced issues 1–4 were fixed after this assessment: a write-once canonical generation plan, create-only chunks/artifacts, durable vision checkpoints, shared vision concurrency control, a disabled-by-default byte cutoff, page-border/rule filtering, search coverage for skipped visuals, and visual fallback after empty PDF OCR. All 523 local tests pass. Real Cosmos/Blob overlapping-writer and resume checks passed, as did a fresh four-format ingestion and both real-model scenarios. See [fault evidence](../../records/phase3b-hardening-conditional-20261026.json), [fresh smoke evidence](../../records/phase3b-hardening-smoke-20261026.json), and the [updated contract](../image-retrieval.md). Post-link lifecycle rereads are also now concurrent. Precise source anchoring, selective previews, more sophisticated figure selection and scale evaluation remain follow-up refinements.

**Current follow-up (2026-10-27).** PDF layout-defined crops supersede the earlier page-rendering path; captions are stored with source images at ingestion; text publishes before vision enrichment; previews are selective; PDF page reads use stored assets. See the [final readiness review](2026-10-27-image-readiness-review.md) for current decisions, checks and remaining limits. Findings below retain their historical reproduction details.

**What fits Cosmos well.** The `/libraryId` → `/documentId` hierarchical key matches the two dominant access patterns: search one library; manage or read one document. The vector shard key remains `/libraryId`. New image rows use the same embedding model and dimensionality as text, so a single ranked query can compare both representations. The generated description and source context make a chart retrievable by natural-language meaning and usable by text-only agents. This is a deliberate description-based retrieval design, not a claim of native image embeddings or complete visual understanding.

Image support retains bounded `TOP` queries, the tested float16 conversion, explicit filter indexing, projections that exclude vectors, and the existing vector/hybrid routing distinction. Internal image references and dimensions do not need ordinary scalar indexes just to be projected. Binary images and signed URLs are not stored in the search index; links are minted on retrieval. These choices are consistent with Microsoft's guidance on colocated data/vectors, scoped search and shard keys. [Vector store documentation](https://learn.microsoft.com/en-us/azure/cosmos-db/vector-search), [performance and partitioning guidance](https://learn.microsoft.com/en-us/azure/cosmos-db/gen-ai/vector-search-performance-tips).

**1. P1 — overlapping attempts can mutate published evidence.** Both workers can pass the pending-generation check at [ingest start](../../src/fli/worker/handlers.py#L181). They then write the same chunk IDs and extraction Blob path. The final conditional document update rejects a loser, but the [artifact overwrite](../../src/fli/worker/handlers.py#L356) happens first. With generated descriptions, repeated processing is not byte-deterministic.

Reproduction: pause attempt A in its vision call; let B finish and publish generation 1; resume A with a different description. The published descriptor initially matches the artifact. After A resumes, it no longer matches, and a full read returns `409 document_text_incomplete`. Active chunks can also acquire A's different descriptions because both attempts upsert the same IDs. This was a controlled overlap, not a failure observed in the live demo. Queue lock loss/redelivery makes overlapping consumers a legitimate failure case; the runtime's renewal-failure callback currently logs the loss without cancelling ingestion. [Service Bus delivery and duplicate-processing guidance](https://learn.microsoft.com/en-us/azure/service-bus-messaging/service-bus-message-loss-and-duplicates).

The fix should make published evidence immutable: either durably establish one canonical generation output using conditional, write-once operations, or isolate each attempt's chunks/artifacts and atomically publish the winning attempt through the control record. Merely rechecking `pendingGeneration` before each write leaves another race. Fencing only the final commit also leaves the data writes unprotected. Cosmos transactions cover a container's logical partition; they cannot atomically encompass the current document container, chunk container and Blob writes. Preserve the publish-pointer pattern, but protect the data it names. [Cosmos transaction scope](https://learn.microsoft.com/en-us/azure/cosmos-db/database-transactions-optimistic-concurrency).

**2. P2 — successful vision work is repeated after downstream failures.** [Vision description calls](../../src/fli/worker/handlers.py#L231) occur before embedding and chunk writes, with no durable description checkpoint. A reproduction with one image, two queue attempts and a simulated embedding failure made two vision calls. With 50 images and repeated deliveries, the avoidable cost can be much larger.

Persist and reuse validated descriptions before advancing to embeddings/writes. A cache identity must include image content, relevant source context, description prompt/version and model configuration; image bytes alone are insufficient when headings or nearby text change. Scope reuse to authorized document/library storage. Couple this work to item 1 so checkpoints do not introduce another overwrite race. Add shared vision concurrency/rate control; vision currently has bounded retries, but no worker-wide governor equivalent to embedding or Cosmos writes.

**3. P2 — candidate selection can exclude the chart the user remembers.** A meaningful 640×400 PNG chart in the existing test fixture compresses to 4,392 bytes and is discarded by the default 10,240-byte cutoff. Dimensions and compressed size are weak proxies for semantic value. The cutoff came from the original plan; the review demonstrates why it needs reconsideration for chart retrieval.

For PDFs, any drawing path qualifies a page for rendering. A three-page reproduction with borders on pages 1 and 2, a chart on page 3, and a cap of 2 retained only the borders. The same mechanism can use the default cap of 50 on decoration-heavy documents. Full-page rendering remains a reasonable fallback for vector charts, but candidate selection should distinguish substantive visual regions from decoration, deduplicate repeated visuals and prioritize meaningful candidates. Skipped-visual counts should also be visible in search coverage, rather than only discovery/full reads. These changes should be evaluated on real reports and decks.

**4. P2 — PDF visual processing can be blocked by OCR returning no text.** [The worker](../../src/fli/worker/handlers.py#L203) continues to visuals for `needs_ocr`, which occurs when OCR is disabled. With OCR configured, an empty OCR result becomes `unsupported` with `ocr_returned_no_text`; the worker fails before inspecting usable visual content. A controlled image-only PDF reproduction returned that failure and made zero vision calls. Text extraction and visual extraction need separate outcomes, followed by a combined decision about whether the document has usable evidence. This does not imply ignoring encryption, corruption or configured processing limits.

**5. Refinements to keep retrieval economical.** Image passages carry nearby text, a heading and document identity, so an agent can recover the explanation today. There is no explicit image-to-source-section/chunk relationship for cheap, precise expansion. Text neighbors use numeric adjacency, while image chunks are appended after all text. A source anchor or related chunk IDs would allow direct document-partition reads for the explanation and make a text hit reliably expandable to its images. This is a data-model improvement, not a need for joins across libraries.

The demo also supplies all returned image previews that fit its allowance, including irrelevant image hits. The vague GDP smoke search returned four images, though the answer needed one. A consuming platform can first inspect descriptions and then materialize selected visuals; the service should preserve IDs/provenance and support that choice. The additional lifecycle point reads for image results are defensible, but the post-link document rereads are sequential. Bounded concurrent point reads could reduce latency without relaxing visibility checks. These are lower priority than items 1–4.

**What remains unproven about “best Cosmos.”** The live image corpus contained four files and seven chunks. It demonstrates ingestion, semantic retrieval and image return; it does not benchmark approximate-search recall, graph traversal, skewed large libraries or simultaneous ingestion/search. Existing E12 evidence already distinguishes small-scope compressed search from graph traversal. Do not infer an index execution mode from this tiny image run, or assume that each small library independently has to reach a documented container-level initialization threshold.

The current Microsoft guide recommends evaluating `quantizedFlat` for smaller scoped datasets and sharded DiskANN for larger scopes. That makes an isolated comparison worthwhile in Phase 4, rather than changing the existing measured configuration from generic advice. Benchmark realistic library-size distributions, exact-search recall, warm index metrics, RU, tail latency, writes and 429s under mixed load. Keep the current defaults and spherical choice until those measurements justify changes. The guide also now describes dropping/recreating vector policies, whereas this repository treats policy settings as permanent; verify that vendor/API evolution with an isolated canary before relaxing the established invariant. [Current index guidance](https://learn.microsoft.com/en-us/azure/cosmos-db/gen-ai/vector-search-performance-tips).

The pre-existing cross-client Session-consistency caveat remains: rereading the control record does not by itself guarantee visibility of another API client's deletion. Worker-wide caps are process-local, so scaling workers also requires aggregate capacity management. Neither issue was introduced by image storage, and neither was resolved by the image smoke check. [Session consistency](https://learn.microsoft.com/en-us/azure/cosmos-db/consistency-levels).

The recommended order is: protect immutable publication; checkpoint expensive vision work; correct the OCR/visual decision and chart-selection rules; add precise image/text expansion and selective visual materialization; then use the planned scale evaluation to choose any Cosmos index or capacity changes. The container and partition architecture can stay in place through that work.
